## 1. What it is and is not

When `ZAPIER_PARSER_ENABLED=true`, every new buy-box version (A4 extraction -> Postgres upsert ->
`buy_box.created|updated` event -> `BuyBoxEventWorkflow`) produces **one email** from the deals
mailbox to a Zapier Email Parser mailbox. A Zap parses it and upserts a row in the operator's
Sheet. That is the whole path.

- The system of record never depends on it: Postgres already has the buy box, and the Sheets sync
  (docs/integrations/sheets.md) already projects it every 15 minutes. The parser path exists for
  operators who want a Zap-driven view or downstream Zaps (Slack, CRM) keyed on buy boxes.
- Nothing flows back. Zapier never calls this system, and nothing reads the Zap's sheet.
- **No second mail transport.** The parser email is an ordinary outbound message: a Graph draft
  that is then sent (INT-13), through the same `create_draft` / `send_draft` activities as
  investor outreach. In mock mode the mock Graph gateway records it; in live mode `send_draft`
  refuses unless `GRAPH_ALLOW_LIVE_SEND=true` (RUL-06), so enabling the parser flag alone sends
  nothing real.
- Default off (RUL-07). With the flag off the activity still runs and records one
  `zapier.parser_skipped` audit note per (buy box, version) with reason `flag_off`, so the trail
  shows the path was consulted.

## 2. `.env` keys

| Key | Meaning |
|---|---|
| `ZAPIER_PARSER_ENABLED` | `false` (default). `true` turns the path on. Human checkpoint: only enable after the Zap below exists. |
| `ZAPIER_PARSER_ADDRESS` | The parser mailbox, `<something>@robot.zapier.com`. With the flag on and this empty, the activity skips with reason `no_parser_mailbox`. |

## 3. The parser mailbox and template

1. Sign in to Zapier and open **Email Parser by Zapier**: <https://parser.zapier.com/>.
2. *Create Mailbox*. Zapier assigns an address like `a1b2c3d4@robot.zapier.com`. Put it in
   `ZAPIER_PARSER_ADDRESS`.
3. Send one sample email to the mailbox so the editor has something to template. In mock mode,
   copy the body of any recorded draft (e.g. from `tests/agents/test_a6.py::GOLDEN_BODY`) and mail
   it from any account; in live mode let the first real buy box arrive.
4. In the template editor replace the sample with the text below (it is generated by
   `wholesaling.integrations.zapier.parser_template()` and matches `A6ParserFormatter` label for
   label). Each `{{name}}` becomes a parser output field.

```
BEGIN_BUY_BOX
FORMAT_VERSION: {{format_version}}
ROW_KEY: {{row_key}}
INVESTOR_ID: {{investor_id}}
INVESTOR_NAME: {{investor_name}}
BUY_BOX_ID: {{buy_box_id}}
BUY_BOX_KEY: {{buy_box_key}}
VERSION: {{version}}
STATUS: {{status}}
SOURCE_MESSAGE_ID: {{source_message_id}}
SOURCE_REF: {{source_ref}}
MARKETS: {{markets}}
CITIES: {{cities}}
ZIPS: {{zips}}
NEIGHBORHOODS: {{neighborhoods}}
ASSET_TYPES: {{asset_types}}
PRICE_MIN: {{price_min}}
PRICE_MAX: {{price_max}}
CONDITION: {{condition}}
STRATEGY: {{strategy}}
FINANCING: {{financing}}
CLOSING_PREFERENCES: {{closing_preferences}}
OTHER_CRITERIA: {{other_criteria}}
UNKNOWN_FIELDS: {{unknown_fields}}
CHANGE_NOTE: {{change_note}}
UPDATED_AT: {{updated_at}}
---
RAW_TEXT:
{{raw_text}}
END_BUY_BOX
```

Format rules A6 guarantees (INT-21 "stable labels and explicit field delimiters"):

- one `LABEL: value` per line, labels upper snake case, always present, always in this order; an
  empty value renders as `LABEL:` (no trailing space);
- every value except `RAW_TEXT` is flattened to a single line; lists are `"; "`-joined; nested
  fields (`CLOSING_PREFERENCES`, `OTHER_CRITERIA`) are compact JSON; money is a plain number;
- `---` separates the structured block from `RAW_TEXT`, which is last and may span lines, ending
  at `END_BUY_BOX`;
- `BEGIN_BUY_BOX` / `END_BUY_BOX` bracket the message so forwarding headers or signatures outside
  them are ignored;
- `ROW_KEY` is `<investor_id>|<buy_box_key>`: the identity of one *logical* buy box across its
  versions. `buy_boxes` is versioned (one Postgres row per version, each with its own
  `buy_box_id`), so keying the Zap on `buy_box_id` would give one sheet row per version; `ROW_KEY`
  gives one row per buy box, which is what INT-22 means by "one buy box";
- subject: `[BUYBOX] <investor_id> <buy_box_key> v<version>`;
- `FORMAT_VERSION` is `1`. Any change to the label set bumps it (`PARSER_FORMAT_VERSION` in
  `a6.py`) and this template must be updated in the same change.

## 4. The Zap

Direct "upsert" is not a Google Sheets action in Zapier, so the Zap is the standard lookup +
branch pattern (INV-20 "lookup + create/update branches if direct upsert unavailable"). Template
listings for the two actions:
<https://zapier.com/apps/email-parser/integrations/google-sheets>.

| Step | App / action | Configuration |
|---|---|---|
| 1 Trigger | Email Parser by Zapier -> *New Email* | Mailbox from §3 |
| 2 Filter | Filter by Zapier | Continue only if `format_version` exactly matches `1` **and** `row_key` exists. Anything else (a forwarded human email, a future format) stops here. |
| 3 Lookup | Google Sheets -> *Lookup Spreadsheet Row* | Spreadsheet: a Zap-owned worksheet (not a tab the sync owns, see note). Worksheet `Zapier Buy Boxes`. Lookup column `row_key`, lookup value `{{row_key}}`. Leave "Create Google Sheets Row if it doesn't exist?" **off**; the branch below makes create vs update explicit. |
| 4 Paths | Paths by Zapier | Path A **Update** when step 3 returned a row; Path B **Create** when it did not ("Row ID does not exist"). |
| 4A | Google Sheets -> *Update Spreadsheet Row* | Row: the `Row ID` from step 3. Map every parser field to its column. |
| 4B | Google Sheets -> *Create Spreadsheet Row* | Map every parser field to its column; `row_key` first. |

Sheet columns, in parser order: `row_key`, `investor_id`, `investor_name`, `buy_box_id`,
`buy_box_key`, `version`, `status`, `source_message_id`, `source_ref`, `markets`, `cities`, `zips`,
`neighborhoods`, `asset_types`, `price_min`, `price_max`, `condition`, `strategy`, `financing`,
`closing_preferences`, `other_criteria`, `unknown_fields`, `change_note`, `updated_at`,
`raw_text`, `format_version`. On the update path the row's `buy_box_id` and `version` move to the
newest version; the full version history stays in Postgres and in the sync's Buy Boxes tab.

Note on which sheet: keep the Zap's worksheet **separate from the tabs the sync owns**. The sync
treats any row it did not write as `sheets_orphan_key` in reconciliation and would overwrite any
cell it did write. A worksheet in the same spreadsheet with a different name (`Zapier Buy Boxes`)
is fine; the sync only touches the tabs in `TAB_SPECS`.

## 5. Acceptance (INT-22)

> Two parser emails changing one buy box update the same row; replaying a parser message causes no
> duplicate.

What the system side guarantees, with the tests that prove it:

| Guarantee | Where |
|---|---|
| Two versions of one buy box are two Postgres rows with different `BUY_BOX_ID`s but the same `ROW_KEY`, so the Zap's lookup finds the existing row and takes the update branch | `tests/integrations/zapier/test_parser_email.py::test_int_22_two_emails_for_one_buy_box_resolve_to_the_same_row`, `tests/agents/test_a6.py::test_row_key_is_one_per_logical_buy_box_across_versions` |
| A replayed message carries an identical `(ROW_KEY, VERSION)` and identical payload, so the lookup finds the row and the update rewrites the same values (no duplicate) | `...::test_int_22_replay_has_identical_replay_key_and_payload` |
| Our side never sends the same (buy box, version) twice, even when the workflow or activity is retried | `tests/activities/test_zapier.py::test_zapier_replay_is_noop` (one Graph send, one `messages` row, one `zapier.parser_sent` event) |
| Flag off -> nothing sent, one audit note | `tests/activities/test_zapier.py::test_flag_off_sends_nothing_and_records_an_audit_note` |
| Flag on in mock mode -> draft then send recorded through the Graph path | `tests/activities/test_zapier.py::test_flag_on_in_mock_mode_drafts_then_sends_through_graph` |

Manual acceptance once the Zap exists (only if the flag is turned on; human checkpoint):

1. Turn the flag on in a non-production `.env`, keep `GRAPH_MODE=mock` or
   `GRAPH_ALLOW_LIVE_SEND=false`, and inject one inbound buy-box email through the mock Graph
   gateway. Confirm a `zapier.parser_sent` audit event and a `messages` row to the parser address.
2. Copy that body, mail it to the parser mailbox from any account: the Zap must **create** one row.
3. Mail it again unchanged: the Zap must take the **update** path and the row count must stay the
   same (replay).
4. Inject a correction ("actually max 300k"): a new version, a new email with `VERSION: 2` and
   the same `ROW_KEY`; the Zap must take the update path and the row must now show
   `price_max = 300000`, `version = 2`.

## 6. Design note on the row key

`buy_box_id` is the id of a **version row** in Postgres (`buy_boxes` is versioned: one row per
version, `is_current` marks the latest), so it cannot be the Zap's lookup key if one buy box is to
be one row. The email therefore carries `ROW_KEY = investor_id|buy_box_key` as a first-class
field (no Zapier Formatter step needed). If an operator instead wants the version history in the
Zap's sheet, switch the lookup column to `buy_box_id`: every version then becomes its own row,
matching the sync's Buy Boxes tab. Nothing on the system side changes either way.
